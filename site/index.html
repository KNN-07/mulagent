Workflow DAG

How the research loop works

Workflows are declarative YAML graphs (research, reproduce, survey, prove, hillclimb). Every loop-back creates new nodes so lineage stays acyclic and resumable from SQLite.

  1. 01 goal

    Set the goal & budget

    Enter a research goal, pick a workflow YAML, and configure your approval policy and compute budget.

  2. 02 scout · surveyor

    Survey papers

    Literature agents query Semantic Scholar, arXiv, and OpenAlex to synthesize baselines, datasets, and open problems.

  3. 03 tournament · gate

    Idea tournament

    The ideator runs an Elo tournament across candidate hypotheses. You choose which directions advance at the first gate.

  4. 04 planner · specHash

    Freeze the plan

    The planner produces an ExperimentSpec whose metric, split, seeds, baseline, and locked eval are hashed before any run begins.

  5. 05 fanout · worktrees

    Run branches on any compute

    Experiment branches reproduce the baseline and fan out in isolated Git worktrees on local, SSH, HPC, or cloud GPUs, alongside optional Lean proof branches.

  6. 06 integrity · critic

    Integrity checks & cross-family critic

    Automated checks verify spec hashes, data leakage, sanity, and bootstrap CIs. A critic from a different model family tries to break every claim in a fresh context.

  7. 07 gate: claims

    Approve claims at gates

    Review run-level evidence, critic attacks, caveats, and Lean axiom checks. Approve with notes, send back for more runs, or reject.

  8. 08 writer · ledger

    Assemble provenance report

    Generate a sandboxed, self-contained HTML report with findings, run tables, inline SVG best-so-far charts, and lineage—every number queried from the ledger.

Default workflow · research.yaml

Plain YAML, acyclic history, zero hidden state

Each node declares its agent role, upstream dependencies, optional human gate, and execution mode (fanout, tournament, join). Workflow agents execute as T3 threads on Claude, Codex, or Gemini providers, while direct role calls use @oh-my-pi/pi-ai.

research.yaml reproduce.yaml survey.yaml prove.yaml hillclimb.yaml
packages/research-core/workflows/research.yaml 
name: research
nodes:
  search: { agent: scout, out: sources }
  survey: { agent: surveyor, needs: [search], out: survey }
  ideas: { agent: ideator, needs: [survey], mode: tournament, gate: pick-ideas, out: ranked-ideas }
  plan: { agent: planner, needs: [ideas], out: specs }
  repro: { agent: experimenter, needs: [plan] }
  preflight: { agent: experimenter, needs: [repro] }
  experiment: { agent: experimenter, needs: [preflight], mode: fanout }
  prove: { agent: prover, needs: [plan] }
  analyze: { agent: analyst, needs: [experiment], mode: join, k: 1 }
  merge: { agent: analyst, needs: [analyze, prove], mode: join }
  review: { agent: critic, needs: [merge] }
  report: { agent: writer, needs: [review], gate: claims, out: report }

Compute adapters

Run experiments on any backend

Every backend implements the same Backend interface (describe, submit, status, logs, cancel, fetch). A scheduler matches each ResourceRequest by cost, queue wait, and priority.

Local

process · container

Run directly as a local process or inside Docker/Podman containers. Workspaces are staged cleanly via rsync into an isolated workRoot.

SSH

remote host

Dispatch experiment jobs directly to remote GPU workstations and servers over SSH with zero cluster control plane required.

SLURM & PBS

multi-node hpc

Generates HPC batch scripts with multi-node allocation (--nodes / select=), checks queues via squeue, sacct, and qstat, and supports preemption-safe checkpoints.

Kubernetes

cluster jobs

Submit, stream logs from, and cancel containerized training and evaluation workloads on Kubernetes GPU clusters.

Modal

serverless cloud

Launch on-demand cloud GPU jobs through the Modal cloud backend adapter alongside local or institutional compute.

RunPod

cloud gpu

Schedule cost-tracked GPU workers on RunPod through the unified cloud adapter and cost-aware scheduler.

One job entrypoint & Python SDK

Jobs run through mulagent-job and log metrics with the zero-dependency mulagent Python SDK. Runs emit METRIC name=value lines (compatible with oh-my-pi’s autoresearch protocol) and post signed receipts over HTTP to the ledger, with optional W&B and MLflow mirroring.

mulagent-job METRIC name=value MULAGENT_LEDGER_URL W&B · MLflow optional

Non-negotiable rules

Agents never type numbers.

Every module in MulAgent enforces six provenance invariants so autonomous loops remain auditable, reproducible, and honest about failures.

RULE 01

Ledger-only provenance

Agents never type a result. Every number in a finding, UI table, or HTML report comes from a RunMetric row in SQLite with its ResearchRunId.

RULE 02

Doer and judge are separate

A critic in a fresh context from the opposite model family attempts to break each finding—challenging seeds, baselines, leakage, and scope—before you see it.

RULE 03

Frozen, hashed specs

Approved ExperimentSpec records are hashed (specHash). The integrity checker flags any run that altered the metric, split, seeds, baseline, or pinned evaluation blob.

RULE 04

Every run is reported

Kept, discarded, crashed, and pruned runs are all recorded in the ledger and rendered in reports—no silent cherry-picking.

RULE 05

3+ seeds and a confidence interval

Claims remain labelled preliminary until the integrity checker verifies all planned seeds, at least three distinct seeds, and a bootstrap CI excluding zero.

RULE 06

State lives in the ledger

Never rely on an agent’s ephemeral context window. Workflow progress, runs, gates, and receipts live in SQLite so any agent can crash and resume cleanly.

Quickstart

Run MulAgent locally

Requires Node 26, vp, and Python 3.10+ in your experiment environment. Open Research → New project in the web or desktop client once running.

01

Install Vite+, clone, and start

bash 
curl -fsSL https://vite.plus | bash
git clone https://github.com/KNN-07/mulagent.git
cd mulagent
vp i
vp run dev

Install Vite+ (vp) on Linux or macOS, then start the MulAgent server and web UI against isolated local state and open the printed URL.

02

Install the Python SDK in your job env

bash 
pip install -e ./python/mulagent
# Optional W&B and MLflow mirroring:
pip install -e "./python/mulagent[wandb,mlflow]"

Provides mulagent-job plus init, log_metric, log_params, seed_everything, and code/data hashing helpers.

03

Add a compute backend (research-backends.yaml)

research-backends.yaml (beside settings.json) 
backends:
  - description:
      id: local
      kind: local
      label: Local CPU
      gpusTotal: 0
      usdPerGpuHour: 0
      healthy: true
      preemptible: false
    workRoot: /var/tmp/mulagent-jobs
    maxConcurrent: 2
    spendCapUsd: 0

Restart the server after adding research-backends.yaml. For workers on another host or inside a container, set MULAGENT_LEDGER_URL in the server environment to an HTTP(S) origin reachable from the worker.
